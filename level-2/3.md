# Module 3 Quiz — Claude Code, MCP & Integration

11 multiple-choice questions (Level 2). Pick the answer(s) the question asks for, then check the answer key at the bottom. Some questions have more than one correct answer or more than four options.
Source: CertSafari Claude Certified Developer – Foundations (CCDV-F) practice quiz, sorted into the five modules by sub-domain.

**1. A team runs the Claude Code GitHub Action so that an @claude comment on a pull request makes Claude push fix commits to that pull request's branch. Their test workflow is triggered on pull_request events and runs for human commits, but it never starts for the commits Claude pushes. The Claude workflow step passes github_token: ${{ secrets.GITHUB_TOKEN }} to the action. What is the most likely cause and fix?**

- A. Commits pushed by an action that authenticates with an API key are not attributed to a user who can trigger CI, so the action must switch to a subscription OAuth token instead
- B. Claude's pushes are being blocked by a read-only contents permission in the Claude job, so contents must be raised to write for the commits to count as real commits
- C. GitHub does not start workflows for commits pushed with the default GITHUB_TOKEN, so remove the github_token input and let the action authenticate as the Claude GitHub App
- D. The test workflow ignores commits from bot accounts, so the Claude identity must be listed in allowed_bots for the test workflow to start on the pull request

**2. A pipeline step runs claude -p to review a pull request. The step must run git diff and read files without any permission prompt, must not be granted blanket permission to run arbitrary commands, and must add a house review checklist while keeping Claude Code's built-in default system prompt. Which flags should the script use? (Select 2)**

- A. --append-system-prompt "<review checklist>" to supply the house checklist, which is added after the default system prompt text.
- B. --permission-mode plan to skip prompts for file reads and diff commands, since plan mode treats read-only Bash commands as pre-approved.
- C. --allowedTools "Read" "Bash(git diff *)" to skip prompts for file reads and diff commands, using permission rule syntax to scope them.
- D. --system-prompt "<review checklist>" to supply the house checklist, which is applied alongside the default system prompt text.
- E. --dangerously-skip-permissions to skip prompts for file reads and diff commands, since the review prompt names the tools it needs.

**3. A developer's project CLAUDE.md should point Claude to a git workflow guide at docs/git-instructions.md, but the guide's full text must not be added to Claude's context at the start of every session. Which approach meets this goal?**

- A. Move the guide into CLAUDE.local.md, since the local file is read on demand while the shared CLAUDE.md is loaded at every session launch.
- B. Move the guide into a .claude/rules/ file that has no paths frontmatter, since unscoped rules files are loaded only when they seem relevant.
- C. Add the path to CLAUDE.md as an @docs/git-instructions.md import line, since imported files are only expanded once Claude actually needs them.
- D. Mention the path in plain words with a note on when to consult it, without import syntax, so Claude opens the file only if it decides to.

**6. A server author wants to ship a reusable "review this pull request" workflow that takes a few arguments, such as the repository and the pull request number. Users should pick it explicitly rather than having the model trigger it on its own. Which MCP server primitive fits best?**

- A. A prompt, because prompts are reusable templates that take arguments and start a task
- B. A resource template, because its parameterized URI takes the repository and PR number
- C. A resource, because resources are the primitive for context the application attaches
- D. A tool, because tools are the primitive for any parameterized operation the model runs

**7. An SDK application registers a UserPromptSubmit hook to catch prompts containing secrets before Claude ever sees them. Which mechanism lets the hook stop the prompt from being processed?**

**8. A team lets Claude Code carry out a large refactor across many files over several days. Some steps run a codemod through shell commands that rewrites files Claude never edited itself, and a subagent also edits files. The team needs a dependable way to undo any single bad step later and to give reviewers a readable history of the changes. What should they rely on?**

- A. Have the agent copy each file to a backup folder before editing it and delete the copies once the refactor is merged
- B. Treat the saved conversation transcript as the change record and resume the same session each day to review what changed
- C. Commit each step to a Git branch as its own small commit, and treat those commits as the record of the refactor
- D. Rely on /rewind checkpoints, which capture every file change the session makes, including shell-command and subagent edits

**9. A plugin maintainer ships internal-tools, which declares the dependency { "name": "secrets-vault", "version": "~2.1.0" }. The secrets-vault plugin is git-backed, its marketplace entry points at 3.0.0, and its repository carries release tags for 2.1.0, 2.1.4, 2.2.0 and 3.0.0. Engineers also have report-gen installed, which constrains the same dependency with >=2.1. Select three statements that correctly describe how Claude Code handles secrets-vault in this setup.**

- A. Auto-update installs the 2.2.0 tag, because the looser >=2.1 range from report-gen takes priority over the stricter ~2.1.0 range from internal-tools
- B. Uninstalling only report-gen frees secrets-vault to move to 3.0.0 on the next update, because the looser >=2.1 range was the one holding it back
- C. Auto-update moves secrets-vault to the 2.1.4 tag, not to 2.2.0 or 3.0.0, because the installed dependency must satisfy both plugins' ranges at once
- D. Installing a third plugin that requires ~3.0 of secrets-vault fails because no version satisfies every range, and existing installs stay unchanged
- E. If both plugins are uninstalled but secrets-vault stays installed, it is no longer range-constrained and tracks its marketplace entry again

**10. A platform team is hardening its MCP configuration for a customer-facing agent. Which of the following configuration choices correctly follow documented guidance for authentication and tool access control over MCP? (Select all that apply.)**

- A. Configuring every MCP server the team has ever evaluated in mcpServers and setting allowedTools: ["mcp__*"] so the agent always has maximum optionality regardless of the task at hand
- B. For a remote HTTP MCP server, placing a bearer token in the headers field of the server configuration rather than appending it to the URL as a query parameter
- C. Passing the GitHub token through the stdio server's env field (GITHUB_TOKEN: process.env.GITHUB_TOKEN) rather than embedding it directly in the command string
- D. Relying on permissionMode: "acceptEdits" to auto-approve MCP tool calls, since accept-edits mode is documented as covering both file edits and MCP tool execution
- E. Using allowedTools: ["mcp__github__*"] to auto-approve every tool from a specific, deliberately chosen server, rather than reaching for permissionMode: "bypassPermissions" to unblock MCP calls generally

**11. A team building a Claude Code agent wants their custom database MCP tool to run without permission prompts, but they do not want to disable other safety prompts elsewhere in the agent. Which approach achieves this?**

- A. Set permissionMode to "bypassPermissions" for the entire session
- B. Set permissionMode to "acceptEdits" so MCP calls are approved automatically
- C. Add the specific tool name, such as "mcp__db__query", to allowedTools
- D. Remove the tool from the "tools" array so Claude always asks before calling it

<summary><b>Answer key and explanations</b></summary>

| Q | Answer | Why |
|---|---|---|
| 1 | **C** | A: Incorrect. An API key or OAuth token only authenticates Claude's model access. The identity used for GitHub operations is set separately by the github_token input, which defaults to the Claude GitHub App, so swapping model credentials does not change whether CI starts. B: Incorrect. The commits already exist on the pull request branch, so Claude is able to push; write access to contents is not what is keeping the test workflow from starting. C: Correct. The documentation says GitHub does not trigger workflows on commits made with the default GITHUB_TOKEN, and that passing it as github_token should be removed so the action authenticates as the Claude GitHub App (or uses a custom app token), after which pull_request-triggered CI runs on Claude's commits. D: Incorrect. The allowed_bots check belongs to the Claude Code GitHub Action itself and stops bots from triggering Claude in a loop; it does not govern whether a separate test workflow starts on a pull request. |
| 2 | **A, C** | A: Correct. --append-system-prompt adds the checklist after Claude Code's built-in default system prompt, so the review keeps that default behavior and gains the house instructions. B: Wrong. Plan mode has Claude research and propose a plan rather than carry out the work, and it does not pre-approve specific Bash commands such as git diff for a headless run. It neither removes the prompts nor performs the review. C: Correct. --allowedTools with permission rule syntax pre-approves the listed tools and commands, so the run does not prompt for them. Nothing broader than file reads and git diff is granted. D: Wrong. --system-prompt replaces the built-in default system prompt with the supplied text instead of sitting alongside it. The review would lose the default behavior and tool guidance that must be kept. E: Wrong. --dangerously-skip-permissions bypasses permission checks for every tool, including arbitrary Bash commands, so it is the blanket permission the step must not have. The tools named in the review prompt do not limit it. |
| 3 | **D** | A: CLAUDE.local.md is appended after CLAUDE.md at launch, so it is loaded into every session too. Moving the guide there changes who sees it, not when it is loaded. B: A rules file without paths frontmatter is loaded at launch with the same priority as the project CLAUDE.md, so moving the guide there still puts all of it into every session's context. C: Imported files are expanded and loaded into context alongside the CLAUDE.md that references them, so an import line brings the whole guide into every session instead of leaving it out until needed. D: A plain-words mention adds only a few tokens, and Claude reads the referenced file only if it decides to open it. Without the import syntax, the file's contents are never added to the launch context. |
| 4 | **C** | A: Incorrect. An SDK MCP server is for custom in-process tools you write yourself, not for connecting to an already-hosted third-party server. B: Incorrect. stdio is for local processes launched with a command; there is no local binary to run here. C: Correct. A documented URL indicates a remote, cloud-hosted server, so the server should be configured with "type": "http" (or "sse") and the given URL. D: Incorrect. "command"/"args" configure a stdio server that spawns a local process; a URL cannot be passed as an argument to achieve HTTP connectivity. |
| 5 | **B, C, E** | A: Incorrect. Endpoints is a generic web term, not one of the MCP-defined capability categories. B: Correct. Prompts are pre-written templates that help users accomplish specific tasks. C: Correct. Resources are file-like data a client can read, such as API responses or file contents. D: Incorrect. Webhooks are not one of the three core MCP server capability types. E: Correct. Tools are functions the LLM can call, with user approval. F: Incorrect. Middleware is an implementation detail of some frameworks, not an MCP capability category. |
| 6 | **A** | A: Correct. MCP prompts are reusable, parameterized instruction templates that are user-controlled: they require explicit invocation (for example from a slash-command menu), accept arguments, and return messages that start the workflow. B: Incorrect. Resource templates are parameterized URIs for read-only data that the application retrieves as context. They supply data to the model; they do not define an explicitly invoked workflow. C: Incorrect. Resources are passive, read-only data sources that the application decides how to use as context. They carry information rather than an instruction template that users pick and fill in with arguments. D: Incorrect. Tools are model-controlled: the model discovers them and decides when to call them. That is the opposite of the requirement that users explicitly choose the workflow rather than letting the model trigger it. |
| 7 | **D** | A: Incorrect. additionalContext only appends extra context alongside the prompt; it does not prevent the original prompt content from reaching Claude. B: Incorrect. permissionDecision inside hookSpecificOutput is the PreToolUse/PermissionRequest control scheme for tool calls, not the mechanism UserPromptSubmit uses to block prompts. C: Incorrect. An uncaught exception is not a documented control-flow mechanism for blocking; hooks are expected to catch errors and return a structured decision instead. D: Correct. UserPromptSubmit uses the top-level decision field; returning decision: block with a reason blocks and erases the prompt before Claude processes it. |
| 8 | **C** | A: Incorrect. Ad hoc backup copies depend on the agent remembering to make them, cannot capture files rewritten by shell commands outside its edits, and leave reviewers with no commit history. They recreate a weaker, manual version of what version control already provides. B: Incorrect. A transcript records what was said and done in one conversation, not a revertible snapshot of the repository, and it is not something reviewers can diff or merge. It also cannot undo a bad step, so it does not provide the rollback or shared history the team needs. C: Correct. The checkpointing documentation says files changed only by Bash commands are not tracked and must be reverted with version control such as Git, that subagent edits are likewise reverted with Git, and that Git provides the permanent history and collaboration that checkpoints do not. Small commits on a branch give a durable rollback point per step and a readable history for reviewers. D: Incorrect. Checkpoints are session-level recovery only: files changed solely by shell commands are not tracked, most subagent edits are not captured, and snapshots are deleted after a retention period. They are documented as not a replacement for version control, and they give reviewers no shared history. |
| 9 | **C, D, E** | A: Incorrect. Auto-update must satisfy every installed plugin's range, not the loosest one. The stricter ~2.1.0 range excludes 2.2.0, so a looser range from another plugin cannot widen what is allowed. B: Incorrect. internal-tools still constrains secrets-vault to ~2.1.0 after report-gen is removed, so the dependency remains held to that range and does not move to 3.0.0. Only removing every plugin that constrains it lifts the restriction. C: Correct. Auto-update fetches a constrained dependency at the highest git tag that satisfies every installed plugin's range. The overlap of the two ranges is 2.1.0 up to, but not including, 2.2.0, so 2.1.4 is the highest qualifying tag and the marketplace's latest version is ignored. D: Correct. A ~3.0 range does not overlap the ~2.1.0 range already imposed by internal-tools, so installing the third plugin fails with a conflicting version requirements message while the existing plugins and the dependency stay as they were. E: Correct. Once the last plugin that constrains a dependency is uninstalled, the dependency is no longer constrained to a version range and resumes tracking its marketplace entry on the next update. |
| 10 | **B, C, E** | A: Incorrect. Configuring every evaluated server and wildcard-approving all MCP tools maximizes both context-window cost and attack surface; this contradicts the guidance to scope allowedTools to the specific servers a task actually needs, and an unanchored wildcard like mcp__* in allowedTools is documented to be ignored with a startup warning rather than granting broad access. B: Correct. The documented pattern for HTTP/SSE authentication is passing headers such as Authorization: Bearer <token> in the server config's headers field, not embedding secrets in the URL. C: Correct. The documented pattern for stdio server authentication is passing credentials through the env field so they aren't hardcoded into the command or args. D: Incorrect. The documentation explicitly states permissionMode: "acceptEdits" does not auto-approve MCP tools; it only covers file edits and filesystem Bash commands, so relying on it for MCP access control is a documented anti-pattern. E: Correct. The documentation explicitly recommends preferring allowedTools wildcards for a specific MCP server over bypassPermissions, since bypassPermissions auto-approves MCP tools but also disables other safety prompts more broadly than necessary. |
| 11 | **C** | A: Incorrect. bypassPermissions does approve MCP tools, but it also disables other safety prompts across the session, which is broader than intended. B: Incorrect. acceptEdits only auto-approves file edits and filesystem Bash commands; it does not auto-approve MCP tool calls. C: Correct. Listing the exact MCP tool name in allowedTools auto-approves only that tool, scoping the exception narrowly instead of disabling broader safety checks. D: Incorrect. Omitting a tool from "tools" removes it from Claude's context entirely, so Claude cannot call it at all rather than being prompted for approval. |
